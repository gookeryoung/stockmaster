## 1. 目标与用户旅程

### 1.1 设计目标

| # | 目标 | 可观测的验收信号 |
|---|---|---|
| 1 | 角色差异一眼可见 | 进入 `/workspace` 3 秒内能说出“我在这里是所有者/编辑者/查看者、能做什么” |
| 2 | 一个任务一个入口 | owner 完成“邀请成员 + 配通道 + 查用量”不需要在全页上下滚动超过 2 屏 |
| 3 | 危险操作有影响面说明 | 删除、转让、移除、清空数据四类操作都先说明“会发生什么”再执行 |
| 4 | 只读态不羞辱用户 | viewer 看到的是“你能看什么 + 找谁申请”，而不是一排灰按钮 |
| 5 | 服务端错误可解释 | 403/404/409 有与 `X-Auth-Error` 对应的中文文案与下一步动作 |
| 6 | 切换工作区不迷路 | 切换后页面明确提示“已切换到 X（角色）”，所有数据随数据源重取 |

### 1.2 三种角色的典型任务

| 角色 | 典型身份 | 一次典型会话要做的事 | 界面必须保证 |
|---|---|---|---|
| owner | 团队负责人陈晓 | 新建「投研小组」→ 邀请 2 人（1 editor、1 viewer）→ 配钉钉机器人 + 邮件 → 设团队预警底线 → 月底导用量 | 成员/通道/策略/删除集中在同一页，且每步有成功反馈 |
| editor | 研究员李雷 | 切到「投研小组」→ 加自选 → 建预警规则 → 跑回测；不改成员、不碰通道 | 写按钮可用；成员/通道只读；看不到明文地址 |
| viewer | 实习生/外部顾问王芳 | 切到「投研小组」→ 看自选、看触发记录、看团队提醒底线；尝试写被拒绝 | 顶部琥珀只读提示；写操作禁用并说明原因；可读区块不隐藏 |

### 1.3 主旅程：从个人空间到团队协作

```text
注册/首次登录
   │  （后端已自动创建 personal 工作区：service.ensure_personal_workspace）
   ▼
个人工作区（自动存在，不可删除）
   │
   │ ① [新建共享工作区] 名称* + 描述
   ▼
共享工作区（创建者 = owner）── 自动切换为当前工作区
   │
   │ ② [邀请成员] ⌕用户名/昵称 → 选角色（编辑者/查看者）→ 添加
   ▼
成员 ≥ 2 ── ③ [通知通道] 添加 Webhook/Bark/邮件 → [测试] → 看到“已送达/未送达”
   │
   │ ④ [用量与配额] 看 8 类资源用量 → [导出 CSV]；管理员按需配 SM_WORKSPACE_MAX_*
   ▼
日常：在顶部切换器换区 → 各页数据随之切换 → viewer 只读、editor 可写
```

失败分支（必须在界面上有落点）：邀请失败 `404 user_not_found / 400 user_disabled /
409 already_member / 409 quota_exceeded`；通道失败 `422 invalid_channel / 409 duplicate_channel /
409 quota_exceeded / delivered=false`；策略失败 `422 范围 / 403`；删除失败
`400 personal_workspace / 409 workspace_not_empty`。

### 1.4 个人工作区语义【现状】

- 注册时由 `plugins/auth/services/service.py` 调 `ensure_personal_workspace()` 创建；存量库由
  `0003_workspaces` 回填；请求解析缺省落到个人工作区（`core/workspace_deps.py`）。
- `kind=personal`，默认名 `<昵称或用户名>的空间`，`owner_id` 为该账号；**不可删除**
  （`400 personal_workspace`）；可改名、可邀请成员共享、也允许转让（原账号下次请求自动补建）。
- 前端文案现状是“可以改名或分享给他人”（`Workspace.tsx:1104`），但页面上没有“分享”入口；
  本文 §4.9 给出口径。

### 1.5 隔离关闭时（`SM_DATA_ISOLATION=false`）的退化体验【现状】

| 位置 | 现状 | 目标（保持） |
|---|---|---|
| 顶部 | `WorkspaceBar` 不渲染（`App.tsx:169` 判断 `config.workspace_enabled && user`） | 不变 |
| 一级导航 | 不出现「工作区」项（`App.tsx:90`） | 不变 |
| 直接访问 `/workspace` | 显示说明卡：“当前未启用数据隔离（SM_DATA_ISOLATION=false）……” | 保留，补一行“如何开启”的环境变量说明 |
| 数据 / 配额 | 所有请求落 `workspace_id=0` 全员共享；`require_editor` 恒通过；`quota.enforce()` 对 `workspace_id<=0` 直接返回 | 不变 |
| 通知通道 / 消息模板 / 预警策略 | 无工作区语义，页面不出现这些区块 | 不变 |
| 管理员 `/workspace` 总览 | 不显示（页面提前 return） | 不变 |

> 设计约束：本分册所有【增量】不得改变上表行为。隔离关闭是单机部署的默认路径，
> 必须保持“没有工作区概念”的完整体验，而不是显示空壳控件。

> 成功标准：owner 首次配置路径 ≤ 8 次点击；任何 4xx 后用户能复述失败原因与下一步；
> viewer 的每个只读区块可读且无“无说明的禁用控件”；切换工作区后 1.5s 内进入新数据态。

### 2.4 信息密度问题（如实描述）

不是“不可用”，而是**角色、任务、风险混排**导致的三类成本：

1. **纵向长度**：桌面 1280px 宽下整页约 3.5–4 屏；owner 为“加一个通道”要滚过用量表，
   为“改模板”要滚到最底。成员表与通道表都只有 4–5 列，却被内联表单撑高。
2. **角色混排**：同一张长页上，viewer 仍看到 5 个卡片、owner 看到 6–7 个，只是按钮显隐；
   `window.confirm` 的移除/转让/删除确认强度一致，危险操作没有独立区域。
3. **反馈粒度粗**：所有操作共用一个顶部 `message`；添加成员失败时错误出现在页顶，
   而不是“按用户名添加”表单旁；`changeRole` 失败只在页顶 flash，字段旁没有任何提示。

其他具体缺口（已核对代码）：

| # | 现状 | 影响 |
|---|---|---|
| 1 | 成员表无“加入时间”列（`WorkspaceMember.joined_at` 已返回） | 无法判断新老成员 |
| 2 | 添加成员只有用户名输入框；`api.workspaceCandidates` 已封装但**未被任何页面调用** | 记不住账号名就无法邀请 |
| 3 | 通道只能启停/测试/删除，`PATCH` 支持的改名/改地址/改类型没有 UI | 换群机器人只能删了重建 |
| 4 | 删除工作区只弹一次 `confirm` 且**固定 `purge=true`**（`Workspace.tsx:1112`） | 用户无法选择“只删空工作区”，与后端 `purge` 语义不对齐 |
| 5 | 消息模板 `maxLength=1024`，后端 `MAX_MESSAGE_TEMPLATE_LENGTH=2000` | 前端比后端更严，长模板被截断 |
| 6 | 趋势图只有 canvas，无数据表替代、无 `aria-label` | 图表信息对读屏/低视力不可得 |
| 7 | 角色下拉包含 `owner` 选项（`Workspace.tsx:810`），后端 `MemberRoleIn` 也接受 owner | 与 [WORKSPACE.md](WORKSPACE.md) §2“owner 只能通过转让产生”不一致（见 §2.7） |
| 8 | 未登录文案“请先登录后再管理**工区**”（`Workspace.tsx:560`） | 错别字 |

## 3. 信息架构与导航【增量】

### 3.1 原则

1. **不新增一级导航**：`工作区` 仍从工作区条右侧「成员与设置」进入（总纲 §4.2、§10）。
2. **切换器是数据源开关**，不是普通菜单：必须同时表达“当前工作区 + 我的角色 + 是否只读”。
3. 工作区页按**任务**分区，而不是按后端模块顺序平铺。
4. 危险操作集中在「概览」的独立危险区，不与日常配置混排。

### 3.2 顶部工作区切换器

目标结构（原生 `select` 保留为无障碍兜底，视觉与角色信息增强）：

```text
┌ 工作区条（桌面） ───────────────────────────────────────────────────────────┐
│ 工作区 [ 投研小组 ▾ ] [所有者]                             成员与设置 →    │
└──────────────────────────────────────────────────────────────────────────────┘
  展开（自定义列表；键盘 ↑↓ + Enter，Esc 关闭）：
   ● 投研小组（共享）         所有者
    我的空间（个人）          所有者
    数据组（共享）            查看者   ← amber 徽章 + “只读”
```

```text
┌ 工作区条（移动 ≈390px） ────────────────────────────┐
│ 工作区 [ 投研小组 ▾ ] [所有者]                        │
│ 只读：你可以查看，不能修改        成员与设置 →        │
└─────────────────────────────────────────────────────────┘
```

规格：

| 元素 | 规格 |
|---|---|
| 触发器 | 显示 `name`（个人工作区带“（个人）”）；`max-w-[14rem]` 截断；列表为空时禁用 |
| 角色 badge / 只读 | `.badge`：owner `emerald`、editor `sky`、viewer `amber`；viewer 追加 `只读` 文本（非仅颜色） |
| 入口与反馈 | 「成员与设置 →」链到 `/workspace`；切换后 toast `已切换到「X」（角色）`，不改 URL |

切换后果（必须在“切换”瞬间可理解）：

| 后果 | 说明 | 处理 |
|---|---|---|
| 数据源切换 | 所有数据请求带新的 `X-Workspace-Id` | `<Routes key>` 重挂载，各 `useQuery` 重取（现状机制） |
| 未保存表单丢失 | 如正在编辑模板/策略，切区后组件卸载 | P0 文案提示；P1 未保存拦截见 §10 #2 |
| 选中失效 | 记住的 id 已被移除/删除 | `refresh()` 回退 personal → 首项；若仍 404，展示 §6 的“工作区不可用”态 |

### 3.3 工作区页分区方案

| 方案 | 结构 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 页内锚点 + 折叠 | 单路由 `/workspace`，顶部子导航 `#overview #members #notifications #usage` | 无路由改动；可搜索/`Ctrl+F`；viewer 可顺序读完；不改变现有书签 | 长页问题只部分缓解 | **P0 推荐** |
| B. Tabs | 同路由内 tab 切换 | 每屏信息少、切换快 | 隐藏信息（viewer 不知道还有哪些区块）；tab 状态易失；与总纲风险 #2 冲突 | P1 可选 |
| C. 子路由 | `/workspace/members` 等 | 可深链 | 新增路由与导航层级，违背“不新增一级入口”；工作区条入口需改 | 不采纳 |

**推荐 A 的理由**：痛点是“找不到 + 危险操作混排”，不是“单页必须隐藏”；4 个任务区块用锚点
足以定位，且 `#members` 可直接作为邀请通知的落地链接；子导航 `sm` 以下横向滚动并高亮当前块。

### 3.4 目标页面骨架【增量】

```text
┌ /workspace ──────────────────────────────────────────────────────────────────┐
│ 工作区设置 · 投研小组                                    （页面标题 + 当前区）│
│ [概览] [成员] [通知] [用量]                    （锚点子导航，sticky）   │
├──────────────────────────────────────────────────────────────────────────────┤
│ #overview 概览+危险区      #members 成员+邀请      #notifications 通道+模板   │
│ #usage 用量/趋势/导出+预警策略                 #all-workspaces 全部工作区     │
└──────────────────────────────────────────────────────────────────────────────┘
```

> 消息模板放在「通知」区末尾：它只影响外发消息，与通道是同一任务的两步。
> 预警策略放在「用量」区：两者都是“团队治理/只读看板”，避免 owner 表单堆叠。

1. 点击列表项 → `select(id)`（改 store + localStorage + `setWorkspaceId`）。

3. 若新工作区请求返回 404（已被移出/删除）：toast 改为
   `「X」已不可用，已切回你的个人工作区`，随后 `refresh()` 重新拉列表。
4. 切换不做二次确认；但若检测到未保存编辑（P1），提示“有未保存修改，仍要切换？”。

在 `/workspace` 顶部条显示“工作区列表加载失败 [重试]”，不影响数据页面（数据请求仍可带旧头）。

空/错/加载：概览数据来自 `list`（已加载）与 `members`；成员列表失败时“所有者/成员数暂不可用”
但不阻塞其它字段；改名提交中按钮文案“保存中…”并禁用。

| 只读 | editor/viewer 看到当前模板（textarea disabled）与占位符说明；无保存按钮 |

（含非法字段名）；403/404 按 §6 处理。模板变更只影响之后的外发消息，历史触发记录不重写。

### 7.2 缺口与最小契约

| # | 能力 | 现状 | 标记 | 最小契约（仅缺失部分） |
|---|---|---|---|---|
| 1 | 成员候选搜索 UI | 端点已存在；前端未接 | **【增量】**（无后端变更） | 调用现有 `GET /members/candidates?search=`；防抖 300ms；无新契约 |
| 2 | 管理员总览搜索/分页 | `?all=true` 一次返回全部，无 `q`/分页 | **【拟新增】** | `GET /workspaces?all=true&q=&page=&page_size=`：`q` 匹配 name/description；响应改为 `{items:[WorkspaceOut], total, page, page_size}`。兼容：不带 `page` 时仍返回裸数组（现有调用方不变） |
| 3 | 管理员「以该区查看」 | 后端已按管理员 owner 放行，但前端 store 列表里没有非成员工作区，切换后 `current=null` | **【增量】**（纯前端） | `useWorkspace` 增加 `selectTransient(workspace)`：把该行临时并入 `list` 并持久化 id；`refresh()` 时若 id 不在本人列表则保留临时项直到手动切走。不改后端 |
| 4 | 管理员总览显示所有者用户名 | 只有 `owner_id` | **【拟新增】**（可选） | `WorkspaceOut` 增加 `owner_username: str = ""`（`GET /workspaces?all=true` 填充）；或前端用 members 反查（P1，无变更） |
| 5 | 成员批量操作（批量改角色/移除） | 无 | **【拟新增】**（P2） | `POST /workspaces/{id}/members/batch`：body `{user_ids:[int], action:"role"\|"remove", role?}`；逐条执行并返回 `{updated:[], failed:[{user_id, detail, code}]}`；最后 owner 保护与配额语义不变 |
| 6 | 通道测试失败原因 | 只返回 `delivered:false`，无法区分地址错误/网络/SMTP 未配置 | **【拟新增】**（可选） | `POST .../test` 响应增加可选字段 `reason?: "smtp_not_configured" \| "network" \| "http_error" \| "unknown"`；旧前端忽略即可 |
| 7 | `PATCH /members/{uid}` 允许直接授予 owner | 与“owner 只能转让”文档语义冲突 | **【拟新增】**（行为收敛） | 后端将 `MemberRoleIn.role` 限制为 `editor\|viewer`，owner 只能走 `/transfer`；返回 422。需确认无 CLI/脚本依赖（见 §10 #3） |
| 8 | 导出文件名取自后端 | 前端硬编码 | **【增量】** | 从 `Content-Disposition` 解析 filename 后设置 `a.download`，回退现名 |
| 9 | 工作区列表变化通知（被移出/删除） | 只在下一次 `refresh()` 发现 | **【拟新增】**（可选，P2） | `GET /workspaces` 已有 `role`；前端 30s 轮询无必要。可先在前端对 404 统一回退，不做推送 |
| 10 | 删除工作区“保留数据”选项 | 无：数据无外键级联，`purge=false` 仅在空工作区可用 | **【拟新增】**（需产品决策） | 如要“删除工作区但把数据移交另一工作区”，需 `DELETE ...?purge=false&move_to=<id>` 或先提供 `workspace claim` 的 Web 版；P0 不做，文案明确“删除会清空数据” |

> 禁止用“前端过滤/前端假分页”假装上表能力（总纲 §0）；#2 的搜索在当前规模下可用前端过滤
> 降级，超过 200 个工作区时必须服务端分页。
